# Figure guide

The three plots are generated; nothing in them is edited by hand. Figures 1(a)
and 2 are hand-authored in the draw.io UI and delivered as finished PDFs in
`figures/final2/`, which is the source of truth for them — `figures/fig1a_concept.pdf`
and `figures/fig2_pipeline.pdf` are copies.

| File | Generated by | Placement in `paper.tex` |
|---|---|---|
| `fig1a_concept.pdf` | copy of `figures/final2/fig1a_concept_optimized_final2.pdf` | Fig. 1(a), `0.545\textwidth` minipage |
| `fig1b_reversal.pdf` | `scripts/make_figures.py` (matplotlib) | Fig. 1(b), `0.435\textwidth` minipage |
| `fig2_pipeline.pdf` | `figures/final2/fig2_pipeline_optimized_final2.pdf` → `scripts/fix_figure_bbox.py` | Fig. 2, full-width `figure*` |
| `fig3_diagnostics.pdf` | `scripts/make_figures.py` | Fig. 3, full-width `figure*` |
| `fig4_depth.pdf` | `scripts/make_figures.py` | Fig. 4, single column |

Rebuild everything:

```bash
cd acl-style-files-master
MPLCONFIGDIR=/tmp/mplcfg python3 scripts/make_figures.py   # the three plots
cp figures/final2/fig1a_concept_optimized_final2.pdf figures/fig1a_concept.pdf
.figtools-venv/bin/python scripts/align_fig2_panels.py \
    figures/final2/fig2_pipeline_optimized_final2.pdf .tmp_aligned.pdf
.figtools-venv/bin/python scripts/fix_figure_bbox.py \
    .tmp_aligned.pdf figures/fig2_pipeline.pdf
rm .tmp_aligned.pdf
```

Both scripts need `pikepdf`, which is not in the system Python. Create their
environment once with
`python3 -m venv .figtools-venv && .figtools-venv/bin/pip install pikepdf pillow numpy`.

`align_fig2_panels.py` puts the four white panel boxes on a common top and
bottom (`y = 46.5 .. 366.0` in the drawing's own coordinates). The exporter
writes each box as its own bezier subpath, and without this step the four boxes
arrive at three different vertical extents — 46.5..366.0, 46.5..362.5, and
48.5..364.5 — which is about a point of stagger once the figure is placed. The
draw.io source `figures/final2/fig2_pipeline_optimized-2.drawio` has the same
alignment applied so a fresh export does not reintroduce it; if you edit the
boxes by hand, re-run the aligner before shipping.

### The draw.io exports crop themselves too tightly

Both files in `final2/` carry a clip rectangle inset from their own MediaBox.
For `fig1a` the artwork fits inside it and the file is usable as delivered. For
`fig2` it does not: the clip ends at `x = 1133.25 pt` while panel 4's box and the
grey zone's border are drawn out to `x ≈ 1153`, so **their right edges are never
painted** and the two boxes render open on the right. Scaling the figure down in
LaTeX cannot fix this — the strokes are not in the file.

`scripts/fix_figure_bbox.py` releases that one clip (leaving the small
`overflow:hidden` clips around individual labels alone), measures what is
actually painted by rendering, and re-crops the page to it with a 2 pt margin.
It prints which edges were being cut, so run it on every fresh export and read
that line:

```
artwork was cut off at: right
```

If it says `nowhere`, the export is fine and the script only tightens margins —
in that case prefer the untouched file, because re-cropping changes the aspect
ratio and Figure 1's minipage widths depend on it.

The two minipage widths are chosen so that both halves of Figure 1 print at the
same height: 1(a) has aspect 1.506 and 1(b) has aspect 1.202, and
`0.545 + 0.435 = 0.98` leaves the `\hfill` a 2% gutter. Both halves land at
164.8 pt. Re-export 1(a) at a different aspect and the widths have to be
recomputed or the panels stop lining up.

Figure 2 is `1137.28 x 300.46 pt`, aspect 3.785, so at `\textwidth` it prints
120.3 pt tall.

The older generator path (`scripts/make_drawio_figures.py` →
`scripts/export_drawio_pdf.js --all`) still builds `fig1a_concept.drawio` and
`fig2_pipeline.drawio` from Python, and its previous outputs are kept in
`figures/.backup_pre_svg/`. Running it now **overwrites the figures with the old
artwork**, so do not run it unless you mean to revert.

## 1. The two things that are easy to get wrong

### Font sizes are in canvas pixels, not points

A draw.io `fontSize` is a canvas pixel count, and the exporter maps the whole
canvas onto the width the figure occupies on the page. So

```
printed_pt = fontSize_px × placed_width_pt / canvas_width_px
```

and the factor differs per figure. This is not a detail: an earlier revision of
Figure 2 looked fine in the draw.io UI and printed its body text at **4.7 pt**,
because the canvas was 1957 px wide and the labels were 20 px.

Measure the delivered PDF rather than trusting the UI. LaTeX scales the whole
page down by `placed_width / pdf_width`, and every `Tf` operand scales with it:

```bash
python3 - <<'EOF'
import re, zlib, collections
pdf_w, placed = 1152.0, 455.24   # pt, pt
d = open('figures/fig2_pipeline.pdf','rb').read()
sizes = collections.Counter()
for m in re.finditer(rb'\d+ 0 obj(.*?)endobj', d, re.S):
    s, e = m.group(1).find(b'stream'), m.group(1).find(b'endstream')
    if s < 0: continue
    try: body = zlib.decompress(m.group(1)[s+6:e].strip(b'\r\n'))
    except Exception: continue
    for t in re.finditer(rb'/\w+\s+([\d.]+)\s+Tf', body):
        sizes[round(float(t.group(1)) * placed / pdf_w, 2)] += 1
print(sorted(sizes.items()))
EOF
```

For `fig1a_concept.pdf` use `pdf_w, placed = 622.08, 0.545 * 455.24`.

The current PDFs still dip under the 7 pt floor the generator enforces: Figure
1(a) runs 6.3–11.6 pt with 3 of 64 runs below 7 pt, and Figure 2 runs 4.0–9.1 pt
with 53 of 114 below. Figure 2's worst are the two illustrative branch quotes at
4.0 pt. Both figures are already placed at their maximum width, so raising the
floor further means enlarging type inside the draw.io source and re-exporting.

### Fonts do not have the glyphs you expect

Times New Roman, Helvetica and Arial all lack `⊕` (U+2295), `✓` (U+2713),
`✗` (U+2717) and `≻` (U+227B); Helvetica also lacks `→` (U+2192). The browser
substitutes a per-glyph fallback without warning — on macOS that is
`STSongti-SC`, so an earlier Figure 2 shipped with a **Chinese font embedded for
its check marks**.

In the generated artwork, checks, crosses and flow arrows are therefore drawn
as vector primitives (`Fig.tick`, `Fig.cross`, `Fig.edge`). `assert_safe_glyphs`
fails the build if any other non-ASCII character reaches a label; extend
`SAFE_NON_ASCII` only after verifying coverage:

```bash
python3 - <<'EOF'
from fontTools.ttLib import TTCollection
cmap = TTCollection('/System/Library/Fonts/Helvetica.ttc').fonts[0].getBestCmap()
print(0x2295 in cmap)
EOF
```

After exporting, confirm what actually got embedded:

```bash
python3 -c "import re; d=open('figures/fig2_pipeline.pdf','rb').read(); \
print(sorted({n.decode() for n in re.findall(rb'/BaseFont\s*/[A-Z]+\+([A-Za-z0-9\-]+)',d)}))"
```

No `STSongti*`, `PingFang*` or other CJK face should appear. The figures in
`final2/` were exported on Linux, so they embed the metric-compatible
substitutes — `LiberationSans` for Helvetica/Arial, `LiberationSerif` for Times
New Roman, `ComicRelief` for Comic Sans MS, and `DejaVuSans` for the arrows and
check marks none of those cover. That set is fine; a macOS re-export is the one
to re-check, because there the arrow falls back to `STSongti-SC`.

## 2. Automatic checks

These run on the Python-generated `.drawio` sources only. Nothing checks the
hand-authored figures, which is why the type-size and glyph audits above have to
be run by hand whenever `final2/` is refreshed.

`make_drawio_figures.py` exits non-zero and prints every problem it finds:

- **Illegible text** — any label under 7 pt at final print size.
- **Unsupported glyphs** — see above.
- **Overrun labels** — real advance widths are read from the font files, the
  text is wrapped the way draw.io wraps it, and a line wider than its cell or a
  label needing more lines than its cell holds is reported. Subscripts (0.7×),
  inline `font-size:Npx` and `<font face=...>` runs are all accounted for.
- **Oversized panel tags** — a title tag wider than the panel it labels.

These catch the defect class that is invisible from XML but obvious in the
render. They do not judge composition; for that, export and look at the PDF at
100%.

## 3. Shared visual system

Colours are defined once at the top of each script and mean the same thing in
all five figures.

| Role | Fill | Stroke |
|---|---|---|
| Reached state / conditioning context | `#DCE7F5` | `#4A7DB5` |
| Recovery, safe branch, selected for training | `#DDEEE6` | `#1F6F54` |
| Harmful branch | `#F8DEDB` | `#C0392B` |
| Our contribution (zone background) | `#EDF3FA` | — |
| Standard machinery (zone background) | `#F4F4F6` | — |
| Primary text and flow arrows | — | `#1A1A1A` |
| Secondary text, frozen components | — | `#6E7681` |
| Hairlines | — | `#C6CDD6` |

Method series in the plots share one grey ramp rather than one hue each: `Base`
`#98A2B3`, `W-DOOR` `#5F6874`, other baselines `#AAB3BF`/`#C6CED8`, CURE-DPO
`#1F6F54`. Only three rows carry the argument, so spending a colour on the rest
makes the reader decode a legend to learn nothing, and the ramp still separates
in grayscale.

Typography and geometry:

- **Prose in Helvetica, every mathematical symbol in Times italic.** Use the
  `m()` and `msub()` helpers so this is consistent; a symbol that appears in
  two faces in one figure reads as a rendering error.
- Type scale, in printed points: panel tags 8.2 bold, box labels 8.0 bold,
  body 7.4, glosses and sub-labels 7.2, never below 7.0.
- Corner radius via `arcSize`; box strokes 1.0–1.6 pt, the emphasized panel
  2.4 pt; flow arrows 2.4 pt with a filled head.
- **Solid outline means trained, dashed means frozen**, stated in the legend.
- No drop shadows, gradients, 3-D effects, clip art or emoji.
- Safe/harmful is carried by a drawn ✓/✗ *and* colour, and selected states by
  fill *and* a heavy border *and* a check, so nothing depends on hue alone.
  Convert to grayscale before submitting and confirm.

Figures 1(a) and 2 depart from the first two rules: they set most labels in
Comic Sans MS, and parts of them still run below the 7 pt floor. Both are
properties of the hand-authored artwork, not of the export, and both need a pass
in the draw.io UI to change.

## 4. What each figure has to say

**`fig1a_concept`** — the model's ordering at the root can reverse once
generation has entered an unsafe state. Two bands with matched geometry, so the
flip is visible in the stroke weights alone: heavy on `refuse` above and on
`harmful` below. `ROOT LEVEL` is glossed *what refusal benchmarks score* and
`REACHED STATE` *what CURE-DPO scores*, which is the whole argument in two
lines. Between the bands, `unsafe prefix accumulates` names the routes into the
state (prefill, jailbreak, tool/RAG, multi-turn drift) so the state does not
look hypothetical, and a dashed red connector labelled `preference reversal`
ties the two margin boxes together. Do not draw a token-level timeline; it
invites questions about which index is which and adds nothing.

**`fig1b_reversal`** — preference reversal (%) per method, horizontal bars
because the names are long, with a dashed line at the Base rate.

**`fig2_pipeline`** — two zone headers carry the contribution boundary that §4.2
states in prose: `STATE SELECTION + SAME-STATE COMPARISON` over panels 1–2 is
ours, `STANDARD: HOW THE PAIRS ARE OPTIMIZED` over panels 3–4 is not. Panel 3's
only assertion is `standard DPO (loss unchanged)`. Panels 1, 2 and 4 each carry
one number the text also reports — six candidate states, 67.7% pair yield,
top-*K* = 2 — so the figure and §4 cannot drift apart silently. The full loss
still belongs in Eq. (7), the halving schedule in Appendix A, and the branch
sources in the caption; an overview builds a mental model, it does not replace
the text. If the zone split changes, §4.1's contribution-boundary sentence and
the caption's opening have to change with it.

**`fig3_diagnostics`** — (a) AUROC forest, six predictors × four separation
regimes, LTRM row highlighted; (b) attack success by recovery-margin bin,
marker area ∝ bin count, with the fitted logistic.

**`fig4_depth`** — attack success against reached-state depth on a log x-axis,
the trained-depth region shaded and the extrapolation region labelled.
